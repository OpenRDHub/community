# 需求书标准骨架（Requirement Doc Template）

从 Khub 项目材料生成需求书时使用的结构。**骨架是固定的，章节按项目实际材料取舍。**

---

## 一、章节选择矩阵

不是每份需求书都需要全部章节。按材料实际内容取舍：

| 章节 | 何时必写 | 何时可省 |
|------|---------|---------|
| 项目背景（疾病/问题概述） | **总是** | — |
| 用户画像与真实痛点 | 有患者材料时 | 纯技术项目 |
| 产品定位 | **总是** | — |
| 核心功能需求 | **总是** | — |
| 非功能需求 | **总是** | — |
| 竞品格局与市场空档 | 有竞品调研材料时 | 无调研材料 |
| 技术路线/可行性 | 有技术材料时 | 纯需求型 |
| **实施范围边界** | 材料中有阶段划分时 | 无阶段划分 |
| 安全/伦理边界 | **总是**（医疗类项目尤其） | — |
| 商业模式/渠道 | 材料中涉及 | 纯技术验证 |
| 附录（来源/术语） | **总是** | — |

## 三、章节写作要点

### 项目背景

- **先给定义再给数据**：读者可能不了解这个疾病
- **数据必须可溯源**：每个数字标出来源
- **区分「疾病本身」与「疾病带来的生活问题」**：需求书关心的是后者

### 用户痛点

- **用原话**：需求提出人的原话是最强证据，直接引用
- **分级而非罗列**：P0/P1/P2 的分级比平铺的清单有用得多
- **证据强度要标**：某个痛点是「9 年跨度 10+ 篇反复出现」还是「个别用户提及」，说服力完全不同

### 功能需求

- **定性痛点 → 量化指标**：这是需求书最核心的转化
  - ❌「提醒要响亮」
  - ✅「强震动 + 声音 + 闪光三通道；持续提醒至实际取药才停止；超时逐级升级」
- **指标要有可验收性**：能写数字就写数字
- **保留需求方原话作为引证**：特别是当指标来自经验值时（如「45 秒是医生经验值」）

### 实施范围边界

- 材料中若反复强调「本次只做 X」，**必须单独立章**
- 用表格明确 in-scope / out-of-scope
- 范围外内容不要展开，但可列为「后续路线」

### 安全与伦理边界

医疗类项目**必写**，且应比材料更严格：

- 数据隐私（匿名化、去识别、最小化）
- 责任边界（不替代诊疗、医生判断优先、不承诺疗效）
- 适用/禁忌范围
- 出现异常时的停止条件

## 四、篇幅参考

| 材料体量 | 需求书页数 | 说明 |
|---------|-----------|------|
| 1–2 份文档 | 6–10 页 | 项目4 乐器改造（1 份 docx） |
| 3–5 份文档 | 12–16 页 | 项目2 鼻腔气流（5 份） |
| 10+ 份文档 | 14–20 页 | 项目1 白化病（13 份 md + 论文） |
| 含完整调研 | 15–25 页 | 项目7 sJIA（含诊断标准） |

**不要为凑篇幅注水。** 材料不足时短一点更好，但要标注缺口。
