# Khub Eval（方案符合度评估 + 改进路线图）

对 Khub 罕见病黑客松（罕见·无界）的赛手方案做两阶段评估：

1. **符合度评估** —— 以需求书功能条目为唯一基准，逐条判定、量化加权、给出综合符合度
2. **改进路线图** —— 诊断差距根因、按投入产出比排优先级、标注时间窗口、给出可执行动作

**评估的落点不是分数，是下一步该做什么。** 只给分不给改进路径的评估是不完整的。

## When to Use

- 「评估赛手方案」「评估方案对需求的解决情况」「符合度评估书」
- 「针对方案，找到对应项目的需求书，评估符合程度」
- 「这个方案怎么改进」「下一步该做什么」
- 新方案提交后需要对照需求书出评估

## 交付物形态

| 交付物 | 性质 | 何时用 |
|--------|------|--------|
| **评估档案** | 定性评述（深度分析、风险、处置建议） | 「给一份评论」「评估回复档案」 |
| **符合度评估书** | 定量评分 + 改进路线图 | 「符合程度」「解决程度」「评分」「怎么改进」 |

**默认产出符合度评估书**（含改进路线图）。用户只要定性评述时给评估档案。两者可对同一方案并存 —— 先要评论后要符合度时，**不要重复上一轮内容**，符合度书应聚焦判定、量化与改进路径。

## 核心纪律

1. **需求书是唯一基准**。方案的创新点、额外价值、技术深度都不计入符合度得分，只在单独章节列示。
2. **以需求条目为主循环**。遍历需求条目去方案里找证据，而不是遍历方案章节看它覆盖了什么 —— 后者会系统性漏掉「方案完全没提」的需求。
3. **区分「设计遗漏」与「进度不足」**。计划书类方案用双口径：设计覆盖度作主基准，当前实现度作附注。
4. **尊重范围边界**。需求书划定的阶段范围之外的内容不计分，但要在「范围外内容」章节列示其后续价值。
5. **逐条判定必须给依据**。引用需求书原文 + 方案原文 + 缺口描述。
6. **不做「平衡性」修饰**。符合度低就是低。但方案的真实优点要单列。
7. **改进建议必须可执行**。带具体动作、时间窗口、可验证目标 —— 不是方向性描述。

## 工作流

### Step 1 — 定位方案与需求书

```bash
# 方案通常在「1.赛手方案」下（可能有多层同名子目录）
lark-cli drive +search --query '赛手方案' --doc-types folder --format json
lark-cli drive files list --params '{"folder_token":"<tok>","page_size":200}' --format json
```

需求书在**项目文件夹**（项目1–8）或本地 `~/Work/hermes-ws/p234678_docs/项目N_需求书.md`。

赛题对应（截至 2026-10）：

| 项目 | 赛题 |
|------|------|
| 1 | 白化病+弱视力+轻便眼镜 |
| 2 | 空鼻症+鼻腔气流模拟分析工具 |
| 3 | 发作性睡病+智能药盒 |
| 4 | 无障碍乐器改造 |
| 5 | Dravet 综合征夜间癫痫睡眠监测设备 |
| 6 | 遗传性视网膜色素变性+游戏辅助工具 |
| 7 | sJIA+合并MAS动态预警平台 |
| 8 | FSHD等手部肌肉萎缩+手部力量辅具 |

### Step 2 — 提取方案全文（按格式分流）

```bash
# HTML：正则剥标签
python3 -c "import re,html; c=open('x.html',encoding='utf-8',errors='ignore').read();\
t=re.sub(r'<(script|style).*?</\1>','',c,flags=re.S); t=re.sub(r'<[^>]+>','\n',t);\
print(re.sub(r'\n\s*\n+','\n',html.unescape(t)).strip())"

# RAR：用 bsdtar（系统通常没有 unrar/7z）
bsdtar -xf 'x.rar' -C outdir/

# DOCX：read_file 直接读
# PPTX：必须同时提取 slide XML **和 notesSlide XML**
python3 -c "import zipfile,re,html; z=zipfile.ZipFile('x.pptx');\
notes=sorted([n for n in z.namelist() if 'notesSlide' in n and n.endswith('.xml')],\
key=lambda x:int(re.search(r'notesSlide(\d+)',x).group(1)));\
[print('==',n,'==\n', '\n'.join(html.unescape(t) for t in re.findall(r'<a:t>(.*?)</a:t>', z.read(n).decode('utf-8','ignore'), re.S) if t.strip())) for n in notes]"
```

**PPTX 备注页是金矿**：真机测试数据、诚实边界声明、技术细节、资料依据路径往往只在备注里，正文幻灯片只有标题。**漏掉备注会严重低估方案。**

### Step 3 — 提取需求条目

**不要跳过这一步直接开始判定。** 详见 [`references/evaluation-rubric.md`](references/evaluation-rubric.md) 第一章。

逐区块提取（痛点映射 / 核心功能 / 汇总表 / 非功能 / 交付物 / 技术参数），原子化、保留原文、编号可追溯、标注 in-scope。

### Step 4 — 逐条判定

六档尺度：完全满足 100% / 大部分 75% / 部分 50% / 少量 25% / 未满足 0% / 不适用（排除）。

**「少量满足」防滥用**：只有「提供素材 / 参照数据 / 方法学来源」才可判 25%。「提到了但没做」「作者知道」「技术上可行」「写在 Roadmap 里」都不可判 25%。

每条判定必须附：需求书原文 + 方案原文 + 缺口描述。详见 [`references/evaluation-rubric.md`](references/evaluation-rubric.md) 第二章。

### Step 5 — 权重与加权

按需求书模块结构分配权重（和 = 100%）。规则：核心/第一刚需 → 最高权重；需求书批评竞品的点 → 权重偏高（差异化关键）。

```
模块符合度 = 该模块内各条目得分的算术平均
综合符合度 = Σ(模块权重 × 模块符合度)
```

### Step 6 — 根因诊断（改进的起点）

把缺失项（0% 条目）列在一起看模式，判定根因。**同一分数可能来自完全不同的原因，改进策略也完全不同**：

| 根因 | 改进策略 |
|------|---------|
| 方法对、对象错 | 换对象，不换方法 |
| 范围错位 | 重划范围 或 转入下阶段归档 |
| 路线不同 | 换交互范式，而非加功能 |
| 软硬失衡 | 补低侧，抢时间窗口 |
| 进度不足 | 按优先级排期，保持范围 |
| 设计遗漏 | 补设计，检查同类遗漏 |

详见 [`references/improvement-playbook.md`](references/improvement-playbook.md) 第一章。

### Step 7 — 构建改进路线图

对每个改进项评估**影响**（Δ符合度）与**成本**，放入四象限：

| | 低成本 | 高成本 |
|---|---|---|
| **高影响** | ① 立即做 | ② 排期做 |
| **低影响** | ③ 顺手做 | ④ 明确不做 |

影响幅度估算：`Δ符合度 ≈ 模块权重 × (改进后模块符合度 - 改进前模块符合度)`

**优先补权重高、当前得分低、条目数少的模块** —— 边际收益最大。

每个 P0/P1 项必须含：具体动作（非方向描述）+ 时间窗口 + 可验证目标。详见 [`references/improvement-playbook.md`](references/improvement-playbook.md) 第二至四章。

### Step 8 — 生成评估书

标准结构（九章 + 附录）：

1. **评估口径** — 判定尺度、权重分配、范围说明（如适用双口径）
2. **核心需求符合度** — 逐条判定
3. **功能需求汇总表符合度** — 需求书若另有汇总表，单独核对
4. **竞品分析对照** — 需求书指出的市场空白，方案填补了几项
5. **非功能需求符合度**
6. **综合评分** — 加权计算表 + 分项速览 + 符合度分布
7. **差距根因诊断** — 缺失项模式 + 根因判定
8. **改进路线图** — 优先级清单 + 落地动作 + 时间窗口 + 可验证目标 + 明确不做的事
9. **结论** — 符合程度判定 + 符合/不符合结构对照表 + 方案真实优点 + 给组织方的建议

**必写的三样**：
- **符合与不符合的结构对照表**（三列：需求书要什么 / 方案给了什么 / 是否符合）—— 比罗列分数更能说明问题
- **差距根因** —— 不是只列现象
- **改进路线图** —— 带时间窗口与可验证目标

### Step 9 — 转 PDF 并归档

```bash
# 中文 PDF：必须用修复过的 ctex 模板（见 chinese-markdown-to-pdf skill）
pandoc x.md --pdf-engine=xelatex --template=/tmp/tpl_fix5.tex -o x.pdf
pdfinfo x.pdf | grep -i pages

# 上传到「方案评估」目录
lark-cli drive +upload --file x.pdf --folder-token <方案评估目录token> --name "符合度评估书NN_<提交人>_项目N_符合度XX.Xpct.pdf"
```

**命名约定**：`符合度评估书{NN}_{提交人}_{方案名}_项目{N}_符合度{XX.X}pct.pdf`

**归档目录**：「1.赛手方案 / 方案评估」（如不存在则创建）

**上传后必须验证**：`lark-cli drive files list --params '{"folder_token":"<tok>","page_size":200}' --format json`

## Pitfalls

- **PPTX 只读正文会漏掉关键信息** —— 必须提取 notesSlide。
- **系统无 unrar/7z** —— 用 `bsdtar -xf` 解 RAR。
- **不要重传用户删掉的文件** —— 上传前先 list 目录确认现状。
- **「评估档案」与「符合度评估书」不要混淆** —— 前者定性后者定量。
- **计划书类方案不能按「已实现」评** —— 用双口径，否则会把「进度不足」误判成「设计遗漏」。
- **方案可能答错阶段** —— 明确判「范围错位」，不给低分后含糊带过。
- **搜索索引有延迟** —— 用 `drive files list` 直接列目录更可靠。
- **markdown 表格里的 `|` 要转义**。
- **不要只给分不给改进路径** —— 评估的落点是行动。
- **改进建议不能是方向性描述** —— 「完善 X 设计」不可接受，要写最小可执行动作。
- **改进建议必须带时间窗口** —— 结构类有前置性，错过 EVT/开模节点就补不上。

## 输出风格

- 判定必须附原文依据，不写「基本符合」这类无锚点结论
- 差距说明要指出**根因**（方法对对象错 / 范围错位 / 路线不同 / 软硬失衡 / 进度不足 / 设计遗漏）
- 改进建议按**投入产出比**排序，每条带具体动作 + 时间窗口 + 可验证目标
- 方案的真实优点要单列，不因总分低而略过
- 给组织方的建议与方案改进**分开列**

## 已验证的评估结论模式

截至 2026-10 的四份评估，根因各不相同，可作为归类参考：

| 方案 | 符合度 | 根因 | 关键改进方向 |
|------|--------|------|------------|
| 乐志亮（项目7） | 27.4% | 方法对、对象错 | 采集层与需求书评分层合并，不推翻重做 |
| 杨国钢（项目2） | 8.7% | 范围错位 | L1.5 几何清单转交阶段一志愿者；情报归档待阶段三 |
| 听野（项目6） | 53.0% | 路线不同 | 呈现层从语言化语音换成空间音频+触觉（换范式非调参） |
| 陈境杰（项目3） | 45.0% | 软硬失衡 | 补硬件侧四项疾病专属设计，抢 EVT 前时间窗口 |

**通用发现**：方案普遍在「自己最擅长的环节」深挖，未按需求书功能清单逐条对齐。建议给组织方提议「需求书条目 → 方案自评」对照表模板。
