# 社区资料归档与运营方案

**供讨论 · 2026-09-28 · 尚未形成社区决议**

日常讨论继续在微信群里进行，飞书用于共同起草和整理文档；把值得接续的过程资料、经过确认的结论和可公开版本沉淀到 GitHub，由一个文档网页提供统一入口。先把这条流程跑通，再考虑文档的自动同步。

## 一、主页保留什么，新增什么

直接以原组织 README 为底稿，保留原文介绍、图片、项目目录和已有章节顺序；本轮纠正主组织徽标、需求池标签和 Follow 入口，补上处理归属。组织首页继续完整介绍 KHub / OpenRD：品牌、社区起源、理念、代表项目、项目目录、共创方式、参与角色、合作与加入入口。新增“社区资料与协作记录”一节，指向资料中心、收录约定和 community。

原 README 的项目与数字保留；外部入口标清组织、个人需求池或上游关系，不把“本轮先建设 community”改写成整个组织的新定位。社区规模和项目进展补统计时点与来源，由维护者核验后更新。现有多个 GitHub 命名空间先说明关系，再决定是否迁移链接。

## 二、四个地方分别做什么

| 地方 | 负责的事情 | 不重复维护的部分 |
|---|---|---|
| 微信群 | 日常交流、提出问题、补充观点和协调行动 | 按主题整理有价值的讨论，不要求逐条搬运聊天记录 |
| 飞书文档 | 多人起草、整理纪要、核对讨论摘要与存放工作材料 | 简单记录可以直接提 GitHub PR，不必每次都新建飞书文档 |
| GitHub community | 保存可追溯的资料版本、讨论摘要、决定记录；通过 PR 审阅修改；Issue 跟进待办 | 同一待办只有一张 Issue；文档引用它，不再复制一套状态 |
| 社区文档网页 | 展示 README、资料分类、全文检索、近期新增与更新、来源与关联事项 | 页面由仓库内容生成，不另建一套文章数据库 |

GitHub 负责共同维护，网页降低阅读门槛。静态网页可以展示和跳转，保存修改仍走 GitHub PR 或飞书起草流程；不把 GitHub Token 放到浏览器里，也不宣称静态网页已经具备多人编辑后台。

## 三、哪些过程资料应该入库

| 内容 | 建议保存方式 | 怎样判断完成 |
|---|---|---|
| 每日新增文件与外部材料 | 按日期建立收录清单；有价值的内容独立成文，其他只登记来源与一句用途 | 来源、日期、用途、访问范围可辨认；没有新增则不用写日报 |
| 会议纪要 | 背景、讨论要点、共识、不同意见、未决问题、后续动作 | 主持人或参与者确认记录准确；没有达成决定就明确写“待讨论” |
| 微信群讨论 | 按主题整理，多天同一话题接在同一记录中，登记来源群代称、日期范围和关键取舍 | 区分原话、整理者归纳和已确认结论；不把聊天投票当正式决定 |
| 重要决定 | 独立决定记录，写清理由、影响、确认方式、生效日期和替代关系 | 可以回答“谁通过什么方式决定、依据是什么” |
| 正式指南、SOP、FAQ | 提炼进长期维护的文档，链接到讨论与决定 | 后来者看现行说明即可开始；历史过程仍能追溯 |
| 附件与素材 | 小型、可分发材料可随记录归档；大文件和受限附件保留原存储与校验信息 | Markdown 中的图片、附件均实际可读，不把外链误当已完成备份 |

过程性内容不必等“完全定稿”才收录。先以草稿状态入库，后续补确认；**PR 合并表示收录了这份记录，不自动表示批准了记录里的提案。**

## 四、日常如何运行

1. **登记来源**：贡献者把飞书链接、文档版本，或微信群某段讨论的主题、日期范围和必要摘录交给资料接待人；不会 Git 的人也可以参与。
2. **整理记录**：按模板写摘要、分歧、未决问题与下一步，给记录一个固定 ID。源文件、修订时间和整理者一并记录。微信讨论可由参与者先在飞书协作整理，也可直接按模板提交 Markdown；不要求每条微信消息都有链接。
3. **核对内容与范围**：由源文档负责人核对准确性，资料维护者检查目录、链接与可见范围。涉及他人的发言与署名，确认适合所选分享范围。
4. **提交 PR**：展示这次新增或改动。无变化的来源版本不重复创建 PR，同一记录更新原文件。
5. **合并并生成网页**：检查通过后生成分类、搜索和更新列表；条目显示本次更新内容，不以构建时间假装文档更新。
6. **接续行动**：确认后的待办转为 Issue，写清产出和接待人；记录只链接 Issue。完成后补结果和贡献署名，更新长期指南。由整理者将记录链接和未决问题回贴原微信群，让参与者方便核对和接续；分享范围须与群成员的访问权限相符。

建议试行节奏：有值班人的工作日集中处理一次新增；会议后两个工作日内整理纪要；每周回看一次待确认资料与失效链接。以上是提议，接待人和投入时间确定后才对外承诺。

## 五、怎样避免飞书和 GitHub 改成两份

微信群是讨论来源，整理后的文档才指定主版本。后续微信讨论出现新信息时，补到同一主题记录并核对，不直接覆盖此前的决定。

每份记录标明 `authority`，只选一个当前主版本：

- **飞书起草阶段**：飞书是编辑主版本；GitHub 保存注明来源版本的快照。飞书改动后，由接待人更新同一记录并发 PR。GitHub 上的修改建议先反馈回飞书。
- **GitHub 维护阶段**：正式指南、决定记录等以仓库为主；飞书原文顶部改成只读说明与 GitHub 链接。需要修改时发 PR。
- **主版本交接**：记录交接日期与双方链接。若两边都发生修改，停止自动覆盖，在 PR 中列出差异，由负责人选择合并方式。

记录正文和元信息存在同一 Markdown 中。索引和网页由脚本生成；分类、日期、来源、状态不再手工复制到几张表。新增过程资料可以先只有中文，保留原文；正式入口、规则和重要决定优先补英文，翻译未更新时明确标记，不阻塞每日收录。

## 六、仓库和网页安排

```text
OpenRDHub/.github
  profile/README.md            # 组织门面与导航
  profile/README.en.md

OpenRDHub/community            # 2026-09-28 按用户指示改为 PUBLIC
  README.md                    # 怎么参与、信息在哪里
  docs/knowledge/              # 资料中心说明与维护约定
  records/
    meetings/2026/             # 会议纪要
    discussions/2026/          # 主题讨论
    decisions/                 # 决定记录与替代关系
    updates/2026/              # 新增材料与阶段更新
  templates/                   # 四类记录模板
  docs/                        # 现行指南和 SOP 索引
  web/                         # 文档站源码，直接读取仓库 Markdown
```

社区级资料放 community；仅涉及具体项目实现的资料放项目仓库，资料中心链接过去。不要为了展示网页再复制一套社区正文仓库，也先不扩建协作平台。

最小元信息包括：固定 ID、标题、类型、发生日期、修订日期、记录状态、公开范围、是否可发布、来源与版本、主版本位置、整理与复核角色、关联记录。原始文件名可以调整，ID 不变。

第一版网页提供：分类与全文搜索、最近更新、状态标签、来源与源文件、会议/讨论/决定互链、下载模板。真实维护入口跳 GitHub 或飞书；本地原型只展示草稿和操作路径。

## 七、同步与发布是两件事

“保存到 GitHub”不等于“全部公开”。微信群聊天原文保留在原沟通范围内；确需保存的摘录和附件按约定放入受限文档。身份资料和未获准公开的患者材料继续放有权限控制的位置；需要 Git 备份的内部文档另放受限仓库。不能用公开仓库里的 `internal/` 文件夹或网页隐藏按钮隔离权限。

community 已按用户明确指示改为 PUBLIC，仓库文件和历史可公开访问；内部原文应留在独立的受限位置。资料的网页发布状态另行维护，不改变 GitHub 的公开可见性。公开构建只取**已审阅且明确允许发布**的文档和附件；页面、搜索索引、raw 下载与 ZIP 一起过滤，不能只在页面上隐藏。

GitHub Pages 可从仓库构建静态网站，但私有仓库不自动意味着网页私有。私有 Pages 的访问控制有 GitHub Enterprise Cloud 条件。当前可直接阅读公开仓库，网页仍为本地预览；部署网站时仅发布允许进入网页的材料，托管方式再按组织套餐选择。[GitHub Pages 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) · [Pages 访问控制](https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site)

## 八、先试两周，再决定自动化

| 阶段 | 具体动作 | 看什么结果 |
|---|---|---|
| 第 1 周 | 指定一名资料接待人和一名复核人；挑选 5–10 份经允许的历史资料；手工跑通导出、整理、PR、网页展示 | 每条能找到来源；没有人把草稿当决议；不熟悉 Git 的伙伴也能交材料 |
| 第 2 周 | 真实跟进一次会议和一轮微信群讨论；更新一份已收录文档；让新人完成一次查找任务 | 能找到上次结论和未决问题；更新不会生成重复记录；后续动作有去处 |
| 试行后 | 若人工整理开始积压，再为明确授权的飞书文件夹做单向导入与 PR 生成 | 重复运行不重复收录、失败有记录、冲突停止覆盖、网页能追溯到来源版本 |

飞书目前支持将云文档导出为 Markdown，但评论不随正文导出；重要批注要先整理进正文，图片与附件链接也须核验。[飞书 Markdown 导出说明](https://www.feishu.cn/content/article/7644456827538820052)

微信群采用参与者按主题整理的流程：记录群代称、讨论日期范围、关键观点、分歧与未决问题；需要核对时，在受限位置保存必要的摘录或截图，并由相关参与者确认摘要。没有可分享的原文链接时，记录来源描述和联系角色即可，不编造消息链接，也不把摘要当成完整聊天备份。本方案不以自动读取微信群消息为前提；后续自动化先处理已整理的飞书文档或 Markdown。

记录整理、校对、翻译、接待和目录维护都作为贡献记录。贡献者可以获得署名、可展示的整理成果、技能反馈和逐步承担维护职责的机会；岗位、费用或其他回报按真实资源另行约定。

## 九、拿到群里讨论的四件事

1. 是否接受“微信群讨论，飞书协作整理，GitHub 保存可追溯版本，网页统一展示”的分工？
2. 谁愿意试行资料接待与复核，能投入多少时间？
3. 哪批现有文档先试，哪些只能内部保存？
4. 主页保留现有内容并新增 community / 资料中心入口，是否符合大家的理解？

本轮交付是本地方案和可点击预览：未接入微信或飞书、未创建仓库、未发布网页、未改变任何现有资料权限。
