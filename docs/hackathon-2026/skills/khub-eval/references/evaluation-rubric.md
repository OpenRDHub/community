# 评估细则（Evaluation Rubric）

符合度评估的完整方法：需求条目提取 → 逐条判定 → 加权评分。

---

## 一、需求条目提取（评估的地基）

**最常被跳过、也最影响结论的一步。** 不先系统提取条目，判定就会漏项、权重就会拍脑袋。

### 1.1 需求书的结构解剖

Khub 需求书通常含以下可提取区块。**逐区块提取，不要只看「核心功能需求」一章**：

| 区块 | 典型标题 | 提取为什么 |
|------|---------|-----------|
| 痛点 → 设计映射 | 「患者痛点 / 需要的设计」两列表 | 每条痛点是一个独立需求条目 |
| 核心功能需求 | 「X.X 功能名」编号小节 | 每条一个条目，子项拆开 |
| 功能汇总表 | 「功能需求汇总表」 | 与上项去重后合并 |
| 非功能需求 | 「非功能需求」章节 | 独立条目，权重通常较低 |
| 竞品空白点 | 「竞品分析」结论 | 不是需求条目，但是**判定的对照轴**（见第五章） |
| 阶段范围 | 「本次实施范围」「不在本次范围」 | 用于划 in-scope / out-of-scope |
| 交付物清单 | 「阶段交付物」 | 独立条目，验收口径 |
| 技术参数 | 「关键技术参数」「验收基准」 | 作为「完全满足」的达标口径 |

### 1.2 提取规则

1. **原子化**：一条需求只描述一件事。原文「强震动 + 声音 + 闪光多通道提醒，持续提醒至实际取药才停止」应拆为两条（多通道 / 持续至取药）。
2. **保留原文**：条目文本用需求书原话，不要转述 —— 转述会引入你的解释。
3. **编号可追溯**：给每个条目分配 ID（如 `R3.1`、`F-07`），判定表和附录共用同一套编号。
4. **标注 in-scope**：对照阶段范围，落在范围外的标 `OUT`，不计分但列入「范围外内容」章节。
5. **去重**：痛点映射与功能汇总表常有重叠，合并时以**更具体的那条**为准。

### 1.3 提取产物

一份扁平条目清单，每条含：ID / 原文 / 归属模块 / in-scope 标记。示例：

```
R3.1 | 盒盖开合自动记录服药 | 服药确认 | IN
R3.2 | 盒体屏幕常显「上次服药时间」，无需操作即可查看 | 服药确认 | IN
R3.3 | 未到安全间隔物理锁定药格，防止重复取药 | 服药确认 | IN
R4.1 | 多药格分区 | 多药管理 | IN
...
OUT-1 | 隐形鼻塞 STL 设计 | 阶段三 | OUT
```

## 二、判定尺度（六档）

| 档位 | 得分 | 判定标准 | 证据要求 |
|------|------|---------|---------|
| **完全满足** | 100% | 已实现，且达到需求书列明的技术口径 | 方案有明确实现描述 + 达到参数 |
| **大部分满足** | 75% | 已实现，但有可明确指出的缺口或未达口径 | 实现存在，缺口具体 |
| **部分满足** | 50% | 方向正确、有实质进展，但仅完成一半或有关键限制 | 有实质产物/设计 |
| **少量满足** | 25% | 提供了关键输入/前提/间接支持，但未实现该功能 | 素材、参照、方法学来源 |
| **未满足** | 0% | 完全未涉及 | — |
| **不适用** | 排除 | 需求书未要求，或方案性质不适用 | 说明理由 |

### 2.1 「少量满足」防滥用规则

这档最容易变成放水工具。**只有满足以下之一才可判 25%**：

- 提供了**可直接使用的素材**（标准几何、开源数据集、现成模型）
- 提供了**参照数据**用于校验（如已发表的正常值分布）
- 提供了**方法学来源**（论文、SOP、协议）

**不可判 25% 的情形**：
- ❌ 「提到了这个概念但没做」
- ❌ 「作者知道这套标准」（知道 ≠ 提供）
- ❌ 「技术上具备条件」（能力 ≠ 实现）
- ❌ 「在 Roadmap 里列了」

### 2.2 各档的证据锚定要求

每条判定**必须**附：
1. 需求书原文（或条目 ID 对应的原话）
2. 方案原文（引用具体句子或章节）
3. 缺口描述（判 75% 及以下时必须写）

**反例**：「方案对提醒功能支持较好，判 75%」—— 无锚点，不可接受。

**正例**：「判 50%。方案硬件具备『震动、屏幕、麦克风、扬声器』（第 4 章架构），有震动+声音+视觉三通道；但需求书要求的『持续提醒至实际取药才停止』未见描述，验收标准（第 8 章）测的是『定时触发 ≥5 次』而非『持续至取药』。」

## 三、权重推导

### 3.1 权重规则（按优先级）

1. **需求书标注为核心/第一刚需的模块 → 最高权重**（如 20%）
2. **需求书批评竞品的点 → 对应模块权重偏高**（说明是差异化关键）
3. **需求书用独立章节展开的 → 中等权重**（如 10–15%）
4. **需求书一笔带过的次要诉求 → 低权重**（如 5%）
5. **权重和必须 = 100%**

### 3.2 计算

```
模块符合度 = 该模块内各条目得分的算术平均
综合符合度 = Σ(模块权重 × 模块符合度)
```

### 3.3 双口径（仅计划书类方案适用）

若方案是**项目计划书/进度表**（描述「打算做什么」而非「做成了什么」）：

| 口径 | 用途 |
|------|------|
| **设计覆盖度**（主基准） | 计划中是否包含该需求的设计 |
| **当前实现度**（附注） | 方案自报的完成状态 |

综合符合度以设计覆盖度计算。附注列示当前实现度，用于区分「设计遗漏」与「进度不足」—— 这两类问题的改进策略完全不同。

## 四、防偏规则

评估者容易犯的四类偏差，逐条设防：

| 偏差 | 表现 | 设防 |
|------|------|------|
| **光环效应** | 方案文档写得漂亮 → 各条目都判高 | 逐条独立判定，先判证据再判分，不看整体印象 |
| **慷慨偏差** | 「人家很努力」→ 给同情分 | 严格按证据锚定；努力程度不是判定依据 |
| **技术深度补偿** | 技术很强 → 功能覆盖不足也给高分 | 技术深度**不计入**符合度，单列章节 |
| **缺失不可见** | 只评方案「有的」，忘了需求书「要的」 | 以需求条目清单为主循环，方案为参照物 —— 不是反过来 |

**第四条最关键。** 正确做法：遍历需求条目，对每条去方案里找证据；而不是遍历方案章节，看它覆盖了哪些需求。后者会系统性地漏掉「方案完全没提」的需求。

## 五、竞品对照轴（独立于评分）

需求书的「竞品分析」章节通常指出了市场空白点。**这些不是需求条目，但应单独做一张对照表**：

| 需求书指出的空白 | 方案是否填补 | 说明 |
|----------------|------------|------|
| （空白点 1） | 完全 / 部分 / 未填补 | 依据 |

这张表的价值：它回答的是「方案相对现有产品有没有进步」，与「方案相对需求书符合多少」是两个不同的问题。符合度低的方案也可能在某项空白上有突破。
